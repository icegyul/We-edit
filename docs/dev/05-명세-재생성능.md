# SPEC-05 재생 성능: 컷에서 끊김 없애기 · 렌더 막대 · 프록시 제안 · 계측

사용자 불만(반복): "프리미어에서는 문제없는 같은 조건인데 이건 느리다", "컷에서 0.5~1초 걸림". 이미 해 둔 것: 하드웨어 디코딩 시험 후 소프트웨어 대체(RTX 3070은 4:2:2 10비트 NVDEC 불가 → 멀티스레드 소프트웨어 59 fps), 장면 축소 박스 필터, 프록시. **남은 가장 큰 원인은 컷 경계에서 디코더가 따라가지 못하는 것**입니다.

## 0. 현재 구조 (코드로 확인, `op-application/src/media.rs`)
- 자산마다 **디코더 스레드 1개**(`Worker`, `decode_loop`). 요청은 `WorkerState.want`(한 칸)에 들어가고 `ahead`만큼 앞을 미리 디코딩(`steer`, `GAP_FILL`, `STEER_RANGE`).
- 프레임 캐시 `FrameCache`(예산 `frame_cache_mb`, 사용자 설정 4096 MB), 키는 `(AssetId, 프레임번호)`.
- 소프트웨어 디코더는 롱GOP 영상에서 임의 위치로 가면 **이전 키프레임까지 되돌아가 디코딩**(탐색 비용). `decoder_seeks()` 계측이 있음.
- **사용자 프로젝트의 특징**: 같은 원본(`C0039.MP4`, 4K 4:2:2 10비트)을 V1(23클립)과 V3(177클립)이 **동시에** 쓰고, 화면 녹화(`2026-10-13 20-31-02.mp4`)가 V2(183클립). 자산당 디코더가 1개라 **같은 원본의 서로 다른 위치 요청이 한 디코더를 두고 다툰다**(탐색 반복).

## 2. P5 먼저: 계측과 합격선 (다른 항목의 판정 기준)
- `op-application/tests/playback_bench.rs`(환경 변수 `PLAY_PROJECT`, `PLAY_START`, `PLAY_FRAMES`, `PLAY_SCALE`)에 **백분위 출력**(p50/p95/최악), `missing_frames`, `decoder_seeks` 증가량, 캐시 적중률을 추가.
- 개발 PC(i7-14700K, RTX 3070)에서 **사용자 프로젝트 사본**(`user1013.wedalur`류, D:에 보관)의 **300초 지점부터 60초**를 1/4 해상도로 재생했을 때 합격선(시작값, 측정 후 조정):
  - 현재 값을 **먼저 측정해 `docs/dev/vendor/PERF.md`에 기록**(변경 전 기준선).
  - 목표: p95 프레임 시간 < 40 ms, 최악 < 100 ms, 누락 프레임 0, 컷마다 100 ms 넘는 정지 0회.
- 재생 중 상태 표시(성능 창): 디코더 탐색 횟수, 누락, 프레임 ms.

## 3. P1 자산당 여러 디코더 (레인)
- `workers: HashMap<AssetId, Arc<Worker>>` → `HashMap<AssetId, Vec<Arc<Worker>>>`(최대 3 레인, 코어 수·메모리로 제한). 요청이 오면 **`last`(마지막 디코딩 위치)가 요청 위치와 `GAP_FILL` 안인 레인**에 보내고, 없으면 놀고 있는 레인, 레인 수가 한도면 가장 가까운 레인을 쓴다.
- 같은 원본을 서로 다른 위치에서 읽는 V1/V3가 **각자 자기 레인**을 갖게 되어 탐색 폭주가 사라진다.
- 레인마다 디코더 인스턴스(하드웨어/소프트웨어 판정 `HW_TRIED`는 공유). 20초 무요청이면 레인 해제(지금 로직 유지).
- **시험**: 같은 파일의 두 위치(0 s, 600 s)를 번갈아 요청 → 레인 1개일 때 대비 `decoder_seeks`가 **90 % 이상 감소**, 결과 프레임 동일. 레인 한도 초과 시 가장 가까운 레인 사용.

## 4. P2 컷 선행 디코딩
- **다가오는 클립 목록**: `op-core/src/plan.rs`에 `upcoming_media(project, sid, t, horizon) -> Vec<(AssetId, SrcTime, Track)>` — 현재 시간 `t`부터 `horizon`(기본 2초) 안에 시작하는 각 트랙의 다음 클립과 그 첫 원본 시간.
- **재생 루프**(UI 프레임마다 `PreviewFrames`가 현재 프레임 요청하는 곳)에서 위 목록의 클립이 **1초 이내**로 다가오면 `MediaService::prefetch(asset, index, priority)`로 **첫 프레임을 키프레임부터 미리 디코딩**해 캐시에 넣는다(P1 레인 사용). 이미 캐시에 있으면 건너뜀.
- 내보내기(`ExactFrames`)는 어차피 순서대로 요청하므로 이득 작음. 재생·스크럽 전용.
- **시험**: 합성 프로젝트(롱GOP 파일에서 임의 위치로 이어지는 컷 20개) 재생 → 컷 직후 첫 프레임 대기 시간 p95가 변경 전 대비 **50 % 이상 감소**, `missing_frames` 0.

## 5. P4 프록시 자동 제안
- 자산을 열 때 측정한 소프트웨어 디코딩 속도가 실시간보다 느리거나(`media.rs`의 `timing` 로직) 4K 4:2:2 10비트이면, 상태줄/자산 목록에 **"이 영상은 무거워요. 프록시를 만들까요?"** 안내(한 번만, 거절 기억). 프록시 생성 기능(`proxies.rs`)은 이미 있으므로 **연결만**.
- 프록시 파일 위치는 **D: 쪽 기본**(C: 용량 문제, `09`의 B-03).

## 6. P3 렌더 막대 (미리 렌더)
- **목표**: 타임라인 눈금자 위에 Premiere처럼 색 막대(빨강 = 캐시 없음·무거움, 노랑 = 일부, 초록 = 캐시됨). `Enter`(또는 `시퀀스 > 작업 영역 렌더`)로 구간을 미리 렌더.
- **캐시**: 프레임 구간별 **내용 해시**(그 구간에 영향을 주는 클립·효과·값·원본 파일 지문)를 키로 `MediaCache\Render\<해시>`에 저장(중간 코덱: 기존 인코더의 가벼운 인트라 코덱, 미리보기 해상도). 편집하면 해당 구간 해시가 바뀌어 자동 무효. 재생 때 해시가 맞으면 캐시를 우선 사용.
- **범위**: 큰 작업이므로 P1·P2로 부족할 때만 착수. 착수 시 별도 상세 설계서(`docs/dev/P3-render-bar.md`)를 먼저 쓴다.
- 합격: 무거운 효과 구간(효과 10개 중첩)을 렌더 후 재생하면 p95 < 40 ms. 편집하면 그 구간만 다시 빨강.

## 7. 순서와 보고
P5(기준선 측정) → P1 → P2 → P4 → (필요하면) P3. 각 단계마다 **기준선 대비 숫자**를 사용자에게 보고(예: "컷 직후 대기 p95 180 ms → 70 ms"). 사용자가 실제 프로젝트를 재생해 체감을 확인.
