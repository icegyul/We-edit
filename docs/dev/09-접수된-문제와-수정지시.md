## B-01 [ ] 내보내기 "화면 끄기"를 체크했는데도 화면이 나온다 (2026-10-14 사용자 접수)

**사용자 말**: "파일 내보내기할 때 화면 끄기 체크했는데, 화면이 나오면서 내보내기를 하고 있다."
**원래 요청(참고)**: "굳이 화면 안 나와도 돼, 체크박스 만들어서 활성화 비활성화 해줘. 저거 나오면 더 느리잖아."

### 증거
- 사용자 스크린샷(2026-10-14): 프로그램 모니터(`프로그램: C0039`)에 **내보내는 장면의 그림이 그대로 나오고**, 아래 막대에 `프레임 내보내는 중: 12418/25662  48 %`(= `export_view`의 문구, `ko.rs`의 `Exporting frame {} of {}`)가 보인다. 그림이 있다는 것은 그 내보내기의 `ExportOptions.preview`가 `true`였다는 뜻이다(`Progress.preview`가 있을 때만 그려짐).
- 그림은 480×270 이하로 읽어 모니터에 늘려 그리므로 흐릿하다. 이 읽기(`read_texture`)가 GPU를 멈추게 해 내보내기를 느리게 한다 — 사용자가 끄고 싶어 한 이유.
- **어느 경로로 시작했는지는 아직 모른다**(대화상자 / AI 도구 / 무음 제거 / 대기열). 그래서 수정 지시 6번의 진단 로그가 필요하다.

### 원인 (코드로 확인한 것 — 사용자가 어느 경로로 내보냈는지는 아직 모름)
화면 = 프로그램 모니터가 내보내는 동안 띄우는 `export_view`(`op-ui/src/monitor.rs`). 그림은 `Progress.preview`가 있을 때만 그려진다(`app/mod.rs`의 `export_preview()`). 그림은 `ExportOptions.preview`가 `true`일 때만 만들어진다(`op-application/src/export.rs`).

### 수정 지시
1. **기본값 뒤집기**: `ExportOptions::default()`의 `preview`를 `false`로. (`export.rs`의 시험 중 `preview`를 기대하는 것은 명시적으로 `true`를 넘기게 고친다.)
2. **모든 시작 경로가 같은 설정을 읽게**: `ExportOptions::from_prefs(&Preferences)` 한 곳을 만들고 대화상자·대기열·MCP(`export`, `export_in_background`)·무음 제거 내보내기가 모두 이것을 쓴다. `ExportJob::start`(기본값 함수) 자체를 없애거나 `#[deprecated]`로 막아 앞으로 실수가 나지 않게 한다.
3. **체크박스를 사용자 말대로**: 문구를 `☑ 내보내는 동안 화면 끄기 (더 빠릅니다)`로 바꾸고 **기본 체크(= 화면 끔)**. 내부 필드는 `screen_off`(참이면 `preview=false`). 환경 설정 키는 `export_screen_off`(기본 `true`). 예전 키 `export_preview`가 있으면 `screen_off = !export_preview`로 한 번 변환하되, **키가 없던 사용자(기본)는 `true`**.
4. **화면을 끄면 모니터에는 간단한 진행 카드만**: 그림 없이 `내보내는 중 · 37% · 남은 시간 4분 12초 · 41 fps`와 진행 막대. 이때 프로그램 모니터가 **뒤에서 영상 프레임을 따로 렌더링·디코딩하지 않는지** 확인한다(GPU·디코더 경쟁이 느려지는 이유). 렌더링하고 있으면 내보내는 동안 멈춘다.
5. **켠 경우**(사용자가 일부러 화면 보기): 지금처럼 200 ms마다 작은 그림을 읽어 보여 준다. 문구에 "켜면 느려집니다" 표기.
6. **진단 로그 한 줄**: 내보내기 시작 때 `export started: <경로> (screen off|on, tuning youtube|delivery)`를 남겨, 다음에 접수가 오면 어느 경로·설정이었는지 바로 알 수 있게 한다.
7. 내보내기 대기열 패널의 항목은 추가한 순간의 설정(`ExportOptions`)을 그대로 쓰므로 3번의 필드명 변경만 따라간다.

### 시험
- `export_options_follow_prefs`: `screen_off = true`로 `from_prefs` → `preview == false`. 기본 환경 설정(키 없음)도 `false`.
- `no_start_path_ignores_the_screen_setting`: 소스 전체를 훑어 `ExportJob::start(` 호출이 시험 코드 밖에 남아 있지 않은지 검사(또는 함수 제거로 컴파일 단계에서 차단).
- `mcp_export_makes_no_picture`: MCP `export_in_background`로 작은 프로젝트를 내보낸 뒤 `Progress.preview.is_none()`.
- `silence_export_makes_no_picture`: 무음 제거 내보내기 경로도 동일.
- `screen_on_makes_pictures`: `screen_off = false` → 그림이 만들어진다(기존 `pause_preview_and_output_rate` 시험 보존).
- `prefs_migration`: 옛 `export_preview: true` → `export_screen_off: false`, `false` → `true`, 키 없음 → `true`.
- 속도: 같은 프로젝트를 화면 끔/켬으로 내보내 `Progress.stage_ms`의 읽기 단계 비교(끔이 더 짧아야 함. 숫자를 보고서에 적는다).

### 합격 기준 (한 문장)
**"화면 끄기"가 켜져 있으면 프로그램 모니터 영역에는 영상 그림이 전혀 없고(검은 배경 + 진행 카드만), 어떤 경로로 시작한 내보내기든 같다.** 위 스크린샷과 같은 상황(48 % 진행 중)에서 그림이 보이면 실패로 본다.

### 확인 방법 (사용자 창에서)
1. 내보내기 대화상자에서 `화면 끄기`가 **기본 체크**인지, 체크하고 내보내면 모니터에 그림이 없고 진행 카드만 뜨는지.
2. 체크를 풀고 내보내면 그림이 나오고, 속도가 떨어지는지.
3. AI 패널에게 "이 시퀀스 내보내 줘"라고 시켰을 때도 그림이 안 나오는지.
4. 무음 제거 → 내보내기 흐름에서도 그림이 안 나오는지.

규모: S(반나절). 관련 명세: `06`(내보내기 화면 항목).

## B-05 [x] AI 편집 도우미 창에 답이 안 보인다 (2026-10-14 사용자 접수, **원인 확정·수정: 커밋 `438bfb5`**, 안전장치 1~6은 선택으로 남김)

**사용자 말**: "AI 창에 '유튜브 타이틀 3개와 본편 내용, 타임코드 정보 정리해서 줘'라고 했는데 대답이 없다."

### 확정된 원인 (사용자 증상: "내 질문도 안 나온다")
대화 목록 스크롤 영역이 바깥 `bottom_up` 배치를 물려받아, 스크롤 영역이 맨 아래에 붙는 상태(`stick_to_bottom`)에서 **줄이 한 화면에 들어갈 수 있는 수를 넘으면(이 칸 크기에서 약 14줄) 줄이 보이는 영역 밖으로 밀리고, 약 20줄부터는 0줄이 보인다.** 첫 질문에서 AI가 받아쓰기를 기다리며 도구를 75번 불러 몇 초 만에 20줄을 넘겼고, 그 뒤 질문과 답이 모두 빈 칸으로 보였다. 수정: 줄을 스크롤 영역 안에서 `top_down`으로 배치(`ai_panel.rs`). 시험: `op-ui/tests/ai_chat_layout.rs`(이전 배치는 50줄에서 0줄, 수정 배치는 14~200줄에서 최신 줄이 보임). 아래 "의심 지점"은 조사 과정의 기록이다.

### 확인한 사실 (Claude Code 세션 기록 `~\.claude\projects\C--Users-Dalur-AppData-Roaming-We-edit-ai\2611b562-….jsonl`)
- AI는 **세 번 모두 답을 만들었다**: 18:35:35(첫 질문, 받아쓰기 2분 뒤), 18:39:05, 18:43:34. 답 안에는 제목 3개·설명란 본문·타임코드·태그가 들어 있다. 즉 **AI가 아니라 창이 답을 보여 주지 못했을 가능성이 높다.** 사용자는 같은 질문을 세 번 반복했다.
- 같은 방식(`claude -p --output-format stream-json --verbose --include-partial-messages …`)으로 재현해 본 결과(사고(thinking) 있는 대화, `--resume` 두 번째 대화, 실제 We edit MCP 도구를 부르는 대화) **창의 처리 규칙(`claude_events` + `poll`)대로 계산하면 답이 모두 표시된다.** → 아직 못 찾은 조건이 있다.
- 사용자 창은 응답 중(`Responding=True`)이었고 멈춘 자식 프로세스는 없었다.

### 의심 지점 (확인 안 됨, 조사 순서)
1. **`poll()`의 `Done` 처리**: 이번 턴에 스트리밍된 글이 한 번이라도 있으면(`streamed = true`) 최종 `result` 문장을 **버린다**. 중간 설명 글(예: "받아쓰기가 진행 중입니다")이 먼저 나온 긴 대화에서 마지막 답이 스트림 이벤트 없이 오면 사라진다.
2. 창이 보이는 방식: 패널 크기·스크롤(`stick_to_bottom` + `bottom_up` 배치), 글 색(`theme::TEXT`, 2026-10-14 팔레트 변경 후) 때문에 AI 줄이 보이지 않을 가능성.
3. 읽기 스레드: `lines().map_while(Result::ok)`는 **UTF-8이 아닌 줄을 만나면 조용히 읽기를 끝내고 `End`로 처리**해 이후 줄(최종 답)을 잃는다. 그 뒤 `poll()`의 `c.wait()`는 UI 스레드를 막을 수 있다.
4. 창이 숨겨진 탭일 때만 `poll()`이 돈다(`show()` 안에서 호출) — 보일 때 한꺼번에 처리되는지 확인.

### 수정 지시 (원인과 상관없이 해 둘 안전장치)
1. **원본 출력 보관**: 각 AI 실행의 stdout 줄과 stderr를 `Logs\ai-last.jsonl`(D: 쪽 로그 폴더)에 기록(덮어쓰기, 최근 1개). 다음 접수 때 **창이 받은 것**을 바로 볼 수 있다.
2. **최종 답 보장**: 실행이 끝났을 때(`End`) 마지막 `result` 문장이 화면의 AI 글에 **들어 있지 않으면 그대로 덧붙여 보여 준다**(스트림 여부와 무관). `streamed` 플래그 방식을 없앤다.
3. **줄 읽기 안전**: 바이트로 읽어 `from_utf8_lossy`로 변환(깨진 줄이 있어도 계속 읽음). 읽기가 끝난 이유(EOF/오류)를 기록.
4. **UI 스레드 보호**: `End` 처리에서 `wait()`로 막지 않기(`try_wait` 후 다음 프레임에 다시).
5. **빈 응답 경고**: 실행이 끝났는데 AI 글이 하나도 없으면 `AI가 답을 보내지 않았습니다 (종료 코드 N). Logs\ai-last.jsonl을 확인하세요`를 **눈에 띄게** 표시(눌러도 반응 없음 금지, 규칙 5).
6. **시험(창 없이)**: `send()`가 실행할 명령을 바꿀 수 있게 만들어(테스트용 가짜 CLI: 줄을 출력하는 작은 스크립트) 다음을 시험한다 — ① 설명 글 + 도구 호출 + 최종 답(스트림 없이 `result`만) → 최종 답이 보임 ② 깨진 UTF-8 줄이 끼어도 뒤의 답이 보임 ③ 출력 없이 종료 → 5번 경고 ④ 두 번째 대화(`--resume`)도 동일. `claude_events`는 이번에 녹화한 실제 스트림(사고 블록 포함 144이벤트 등)을 고정 입력으로 쓴다.
7. 사용자 화면 확인 질문은 `docs/dev` 대화 기록 참조: 질문 아래에 무엇이 보였는지(아무것도 없음 / get_sentences 줄 / 경고 줄 / 잠깐 보였다 사라짐 / 창 멈춤)가 원인 좁히기의 핵심.
